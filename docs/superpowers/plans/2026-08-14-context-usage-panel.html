Context usage panel — dock, drag, resize

Implementation plan for xuzhougeng/wisp-science · behavior approved via interactive mock and review · 2026-08-14

1Background

Wisp's chat composer carries a small gauge next to the model picker. Clicking it (or typing /context) opens the context usage panel: a card showing how full the model's context window is, broken into seven colored categories — system prompt, tool definitions, built-in rules, skills guidance, MCP tools, subagents, and conversation — with a stacked bar and expandable rows that reveal the underlying text (the actual system prompt, the actual tool schemas). The panel was introduced in PR #662 (2026-08-04), narrowed to the composer's width in #665, given expandable rows in #680, and its gauge tied to the session's model in #713. That work settled how the panel relates to the composer; how it relates to the conversation was never addressed, and that is what this plan changes.

Three problems with the current behavior

It covers the conversation. The panel is an absolutely-positioned overlay floating above the composer, so opening it hides the newest messages — exactly the content you want visible alongside it, since when context is filling up, the turn responsible is usually the last one in the transcript. Reading both currently means opening and closing the panel repeatedly.

It cannot be moved or resized. Position and size are fixed in CSS. Expanding a row like "System prompt" squeezes thousands of tokens into a small scrolling box that cannot be enlarged.

It swallows the first click. An invisible full-screen layer sits behind the panel to catch outside clicks and dismiss it. Clicking into the message input therefore closes the panel but does not place the cursor — the click dies on the invisible layer, and a second click is needed to start typing. The same is true of every other control in the window while the panel is open.

Overall goal

The context usage panel becomes a well-behaved workspace surface instead of an obstruction. It opens docked above the composer, pushing the conversation up so the newest reply stays visible; it can be dragged off its dock into a floating window that stays open while you type; and it can be resized, with its bar and rows reflowing to fit. The invisible click-swallowing layer is removed entirely. Panel content — the seven categories, their accounting, the expandable details — does not change, and nothing in the Rust backend is touched.

Overall deliverables

Three small PRs (dock → float → resize) plus a polish/QA pass, matching the repo's one-abstraction-per-PR rule. Each PR ships with updated Playwright coverage in ui-tests/tests/ui.spec.ts and documentation updates (docs/ui-design-principles.md, design-qa.md). All changes land in ui/ + tests + docs — zero store migrations, zero Tauri command changes.

2Specified behavior

These are decisions, not options — reviewed and approved against a working interactive mock. Each carries its rationale so the spec stands on its own.

B1Two states: docked and floating

The panel has exactly two states. Docked — its home: sitting in the layout between the conversation and the composer, matching the composer's width, pushing the transcript up rather than covering it. Floating — a free window the user has dragged anywhere on screen. There is no third state and no overlay state; the current overlay behavior is removed, not kept as a fallback.

Why: docked preserves the "click the gauge, see it right there" immediacy the panel was designed around; floating exists for the moments you want to study the panel while continuing to work. Docked width stays locked to the composer — that was settled in PR #665 after explicit user feedback, and this plan doesn't reopen it.

B2Docked: the conversation moves up, never behind

Opening the gauge inserts the panel into the layout flow. The transcript shrinks to make room and auto-scrolls so the latest message sits against the panel's top edge; closing the panel returns that space and restores the reading position. The docked panel may take at most 46% of the window height. Expanding a row scrolls inside the panel rather than growing it, so the conversation never loses more than half the screen.

Why the cap: the seven rows plus header fit comfortably under it at every supported window size, while a fully-expanded "Tool definitions" row could otherwise consume the whole viewport. Users who need more room than the cap allows have floating mode (B3) and resize (B5).

B3Floating: drag the header to break it free

Dragging the panel's header more than ~8px undocks it: the panel detaches and follows the cursor, landing wherever it's released. While floating it shows two extra affordances — a dock-back button in the header and a resize grip in the bottom-right corner. Double-clicking the header, or pressing the dock button, snaps it back above the composer. Dragging near the dock position does not auto-snap; re-docking is always an explicit action. The panel is always clamped to the window; it can never be dragged or restored to an off-screen position.

Why no snap zones: magnetic behavior is easy to trigger accidentally and hard to discover deliberately; two explicit re-dock gestures cover the need. Why the 8px threshold: a plain click on the header must stay inert so misclicks never fling the panel.

B4Dismissal depends on the state

Closes the panel…DockedFloating
Clicking into the message inputyesno — stays open while typing
Clicking anywhere else outside the panelyesno
Escape (topmost surface only, single press)yesyes
The × button / re-clicking the gaugeyesyes
Switching to another conversationyesyes

In every dismissal case the triggering click also lands: clicking the input closes the docked panel and places the cursor; clicking a sidebar session closes it and switches to that session. Nothing swallows clicks anymore — this is a deliberate window-wide behavior change, not a side effect.

Why the asymmetry: a docked panel occupies the space you're typing toward, so stepping aside on input focus is the courteous default. A floating panel was deliberately parked somewhere out of the way — dismissing it on typing would defeat the only reason it exists. Both halves of this rule were explicitly confirmed in review.

B5Resizable when floating, reflowing content

The corner grip resizes a floating panel between a 320×220px minimum and the window bounds. The stacked bar, category rows, and any expanded detail block reflow to the new size — the bar's segments are proportional widths, and the detail area's height follows the panel instead of being fixed. Docked mode has no manual resize; its size is the composer's width and the content's height under the B2 cap.

B6What the panel remembers

Floating position and size persist (locally, per machine — the same mechanism that remembers the composer's custom height). Within a running session, reopening the panel restores its last state: closed while floating means it reopens floating, in the same place. After an app restart the panel opens docked, but a previously saved floating geometry is still there the next time it's undocked. Remembered geometry is clamped to the current window on restore, so a smaller window never resurrects an unreachable panel.

B7No state indicator

Nothing labels the panel "docked" or "floating". The geometry is the signal: a docked panel visibly sits in the layout; a floating one visibly doesn't, and carries the dock button and resize grip. An earlier draft used a text chip and it was rejected in review as redundant.

B8Small windows follow the same rules

No special-casing below the 960px breakpoint where Wisp's Inspector becomes a drawer: the same clamps simply bind tighter — a floating panel can't exceed the window minus margins, and the docked cap still holds. Floating remains available at every size.

3Delivery steps

Sequenced so each PR is independently shippable and user-visible. PR 1 alone already resolves two of the three problems in §1.

PR 1

Dock the panel; delete the click-swallowing layer

no dependencies
Goal

The panel never covers the conversation, and no click is ever swallowed.

Deliverable

Behaviors B1-docked, B2, and the docked column of B4: the panel opens in layout flow with the transcript auto-following, height capped, and every dismissal path working without consuming the triggering click. The backdrop element is deleted outright.

Done when

Playwright proves: latest message visible with the panel open · first click into the input places the caret · a click on another control both dismisses and activates · Escape pressed immediately after opening closes only the panel · scroll position restores on close. Docs: placement paragraph in ui-design-principles.md rewritten; existing overlay-behavior tests updated, with the panel-width-equals-composer assertion retained for the docked state.

PR 2

Drag to float; state-dependent dismissal; memory

depends on PR 1
Goal

The panel becomes a companion you can park anywhere and keep open while typing.

Deliverable

Behaviors B3, the floating column of B4, B6, and B7: header drag past threshold undocks at the cursor with viewport clamping; floating ignores typing and outside clicks; dock button and double-click re-dock; geometry persisted and restored. A dock icon is added to the shared compose_icon set.

Done when

Playwright proves: drag undocks and position sticks · typing while floating leaves the panel open and keystrokes reach the input · Escape still closes topmost-first when another overlay sits above the panel · reopening restores state and geometry · both re-dock gestures work. Tooltip strings added for both locales.

PR 3

Resize with automatic reflow

depends on PR 2
Goal

Long details — a 3.4K-token system prompt, dozens of tool schemas — become readable by making the panel bigger.

Deliverable

Behavior B5: corner-grip resize with clamps; bar, rows, and expanded details reflow; the detail block's height derives from the panel's height instead of a fixed 240px; size persists alongside position.

Done when

Playwright proves: resizing changes the rendered box within clamps · the bar still spans its full new width · an expanded detail grows with the panel · minimums hold.

PR 4

Polish and QA pass

independent, last
Goal

The feature holds up in dark theme, small windows, and both languages — and the repo's design record reflects the new behavior.

Deliverable

Dark-theme and narrow-breakpoint verification (the gap design-qa.md already lists as open), motion on Wisp's --motion-* tokens with prefers-reduced-motion respected, the design-qa.md comparison record refreshed, and the upstream issue (if filed) updated with what shipped.

Done when

Screenshots in both themes at 1100px and below 960px attached to the PR; the full verification suite green on all three OS targets in CI.

4Consciously deferred

Considered and set aside — listed so a future reader knows they were choices, not oversights.

Magnetic snap-back zones near the dock (B3 keeps re-docking explicit) · per-project rather than per-machine geometry memory · manual height adjustment of the docked panel · all-edge resizing · keeping the panel open across conversation switches · disabling floating below 960px. Any of these can be layered on later without disturbing the architecture; none blocks the PRs above.

State model

  • Signals: context_usage_open: bool (exists) plus context_usage_mode: Docked | Floating, context_usage_geom: Option<(f64,f64,f64,f64)>, and context_usage_dragging / _resizing: bool — flat root-owned RwSignals, matching the codebase's no-store convention.
  • Drag and resize reuse the existing capture pattern: a *_dragging signal conditionally renders the full-screen .drag-overlay (right-pane.css:5) carrying mousemove/mouseup, exactly like the five existing one-axis resizers. Positioning via left/top like the rest of the app (no transform-based positioning, for WebView2/webkit2gtk consistency).
  • Dock-state scroll: on open/close, reuse schedule_chat_follow() — the same call on_composer_resize_end makes — so the transcript keeps its bottom pin without new scroll code.
  • Outside-click dismissal (docked) uses a non-capturing document listener that checks the click target against the panel and never calls preventDefault/stopPropagation — that is what makes B4's "the click also lands" guarantee hold.

Semantics, accessibility, and the Escape stack

  • Drop aria-modal="true" in both states — it was already inaccurate (focus never moves into the panel). Keep role="dialog" + aria-labelledby; the floating panel is a non-modal dialog.
  • Escape handling stays in the app-level ordered chain (topmost surface first), one entry, both states. Tests press Escape immediately after opening without moving focus first, per the repo's AGENTS.md rule.
  • The drag threshold keeps a plain header click inert; the header's buttons are excluded from the drag surface.

Risks and mitigations

  • Scroll anchoring regressions — this area has history (#670: chat jumps to top during streaming; #849: scroll position across sessions). Mitigation: dock insertion/removal goes through schedule_chat_follow() only; PR 1 adds a test that streams a reply with the panel docked and asserts the viewport stays pinned.
  • Animation vs. test flakiness — the panel's enter animation is long enough to make a mid-animation assertion see a transparent panel (observed during mock verification). Tests assert post-animation state via expect.poll on geometry, never fixed sleeps; motion uses Wisp's --motion-* tokens and respects prefers-reduced-motion.
  • One-click outside dismissal surprises — B4's "click also lands" applies window-wide. If a specific control turns out to be dangerous to hit through a dismissal (none identified so far), an exemption is a contained change in the dismiss listener, not a layout rework.
  • Geometry restored off-screen after a window shrink — the restore path clamps to the live viewport before the floating panel's first paint.

Verification (per AGENTS.md)

  • cargo fmt --all -- --check · cargo test --workspace
  • cd ui && cargo check --target wasm32-unknown-unknown
  • cd ui-tests && npm ci && npx playwright test
  • Manual smoke on Windows + macOS: drag/resize feel, dark theme, Zh locale, 960px breakpoint.

Out of scope: panel content and bucket accounting (wisp-core), the gauge trigger, ACP single-total sessions (they get the same panel shell with one row — behavior identical), store/migrations, any Tauri command.
